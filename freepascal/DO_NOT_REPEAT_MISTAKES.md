# รวมบทเรียนและข้อห้ามทำเด็ดขาด (DO NOT REPEAT THESE MISTAKES)
**บันทึกกฎความจำและข้อผิดพลาดที่ห้ามทำซ้ำในระบบ FreePascal SSO (`fpsso`) และ RADIUS (`fp-radius`)**

---

## 🚫 ข้อห้ามที่ 1: ห้ามส่ง Handshake ผ่าน `<iframe>` ซ่อน (Hidden Iframe)
* **สิ่งที่ไม่ควรทำ:** ใช้ `<iframe name="target_frame">` แล้วสั่ง `form.target = "target_frame"` เพื่อแอบส่งข้อมูลไปที่ FortiGate
* **ผลกระทบที่เคยเกิดขึ้น:** พอร์ต `1003` ของ FortiGate (`https://192.168.200.1:1003`) เป็น HTTPS ที่ใช้ใบรับรอง Self-Signed ตัวเบราว์เซอร์ (Chrome) จะบล็อกการยิงคำขอใน `<iframe>` เงียบๆ ทำให้ FortiGate ไม่ได้รับข้อมูลล็อกอิน ส่งผลให้ **"ผู้ใช้เห็นหน้าสถานะ แต่ไม่มีสิทธิ์ออกอินเทอร์เน็ต"**
* **✅ วิธีที่ถูกต้องและถาวร:** ต้อง Submit ฟอร์มบนหน้าต่างหลักของเบราว์เซอร์โดยตรง (Top-Level Form Submit) เท่านั้น

---

## 🚫 ข้อห้ามที่ 2: ห้ามแปลงพอร์ต `1003` เป็น `1000` เองโดยพลการ
* **สิ่งที่ไม่ควรทำ:** เขียนโค้ดแปลง URL จาก `https://...:1003/fgtauth` ให้เป็น `http://...:1000/fgtauth`
* **ผลกระทบที่เคยเกิดขึ้น:** บน FortiGate อาจเปิดเฉพาะพอร์ต 1003 (HTTPS Auth) และปิดพอร์ต 1000 ทำให้เมื่อยิงไปพอร์ต 1000 แล้ว FortiGate ไม่ตอบรับ ส่งผลให้ไฟร์วอลล์ไม่อนุญาตให้ออกอินเทอร์เน็ต
* **✅ วิธีที่ถูกต้องและถาวร:** ให้ส่งคำขอไปยัง URL และพอร์ตที่ FortiGate ส่งมาในพารามิเตอร์ `post` เสมอ

---

## 🚫 ข้อห้ามที่ 3: ห้ามลืมแนบ `?sid=` ใน URL Redirection ของ FortiGate
* **สิ่งที่ไม่ควรทำ:** ส่ง `redir` และ `4Tredir` เป็น URL โล้นๆ เช่น `https://auth.kpo.go.th/sso/status` โดยไม่มี `sid`
* **ผลกระทบที่เคยเกิดขึ้น:** เมื่อ FortiGate ทำการ 302 Redirect ข้ามโฮสต์จาก `192.168.200.1` กลับมาที่ `auth.kpo.go.th` ตัวเบราว์เซอร์จะตัด Cookie `SSOSESSID` ทิ้ง ทำให้หน้า `/sso/status` หา Session ไม่เจอ และเด้งผู้ใช้กลับไปหน้า Login วนลูป
* **✅ วิธีที่ถูกต้องและถาวร:** แนบ `?sid=<SessionID>` ไปในพารามิเตอร์ `redir` และ `4Tredir` เสมอ เพื่อให้หน้าสถานะกู้คืน Session ได้ 100%

---

## 🚫 ข้อห้ามที่ 4: ห้ามบันทึกเฉพาะ `MD5-Password` ลงตาราง `radcheck`
* **สิ่งที่ไม่ควรทำ:** เวลาสร้างผู้ใช้ SSO (ThaID, Provider ID, Google) บันทึกเฉพาะ MD5 Hash ลงในตาราง `radcheck`
* **ผลกระทบที่เคยเกิดขึ้น:** FreeRADIUS และ `fp-radius` ใช้ `Cleartext-Password` ในการยืนยันตัวตนกับ FortiGate เมื่อไม่มี Cleartext ทำให้ FortiGate ได้รับ Access-Reject ส่งผลให้ **"ผู้ใช้ ThaID ล็อกอินผ่านเว็บได้ แต่ไฟร์วอลล์ไม่อนุญาตให้ออกอินเทอร์เน็ต"**
* **✅ วิธีที่ถูกต้องและถาวร:** สำหรับทุกช่องทางการล็อกอิน จะต้องลบข้อมูลเดิมที่ซ้ำซ้อน และบันทึกรหัสผ่านลง `radcheck` **ทั้งแบบ `Cleartext-Password` และ `MD5-Password`** ควบคู่กันเสมอ

---

## 🚫 ข้อห้ามที่ 5: ห้ามส่งฟิลด์ `answer=1` ไปยัง FortiGate
* **สิ่งที่ไม่ควรทำ:** ส่ง `<input type="hidden" name="answer" value="1">` ในฟอร์ม Handshake
* **ผลกระทบที่เคยเกิดขึ้น:** ทำให้ FortiOS เข้าใจว่าเป็นการตอบรับจากหน้า Keepalive Portal และจะแสดงหน้าต่างสีขาวของ FortiGate ค้างไว้ แทนที่จะทำการ 302 Redirect กลับมาที่หน้าสถานะ
* **✅ วิธีที่ถูกต้องและถาวร:** ส่งเฉพาะ 5 ฟิลด์มาตรฐาน: `username`, `password`, `magic`, `4Tredir`, `redir`

---

## 🚫 ข้อห้ามที่ 6: ห้ามพึ่งพา หรือเรียกใช้ PHP โดยเด็ดขาด
* **สิ่งที่ไม่ควรทำ:** พึ่งพา php-fpm, mod_php หรือเขียนโค้ดเรียกไฟล์ PHP ภายนอก
* **✅ วิธีที่ถูกต้องและถาวร:** ระบบ `fpsso` และ `fp-radius` เป็น Pure Native FreePascal Binary 100% แยกเด็ดขาดจาก PHP

---

## 🚫 ข้อห้ามที่ 7: ห้ามปล่อยให้ Database Transaction ใน `fp-radius` ค้างโดยไม่ Commit
* **สิ่งที่ไม่ควรทำ:** เปิด `Query.Open` แล้วไม่สั่ง `Query.Close` และไม่สั่ง `Transaction.Commit` ใน Worker Thread ของ RADIUS
* **ผลกระทบที่เคยเกิดขึ้น:** Transaction ค้างในสถานะ Active หรือเมื่อ MySQL Connection หมดเวลา (Timeout) คำสั่งตรวจรหัสผ่านรอบถัดไปจะ error ส่งผลให้ **"FortiGate ได้รับ `Auth=Failed` และไม่อนุญาตให้ออกอินเทอร์เน็ต"**
* **✅ วิธีที่ถูกต้องและถาวร:** ทุกครั้งหลัง Query ต้อง `Query.Close`, `Commit`/`Rollback` Transaction ทันที และมีระบบ Auto-Reconnect หาก Connection ขาดหาย
